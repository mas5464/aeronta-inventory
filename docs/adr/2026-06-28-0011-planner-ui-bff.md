# ADR-0011: #7 Planner UI — backend-for-frontend (BFF) in agent-spine

**Date:** 2026-06-28
**Status:** Accepted
**Context project:** #7 Planner UI "Trax IO Review" (BFF slice; React frontend is the next slice)

## Context

The Planner UI is the sole customer-facing surface for reviewing/approving the agent's recommendations. The design splits it into a **React frontend embedded in eMRO** and a **Trax-owned Python FastAPI backend-for-frontend (BFF)**. Today the reco-API is read-only and the Agent Spine is CLI-only: the `ApprovalTask` queue the Supervisor produces is **ephemeral** (printed as JSON, then lost). Before a React app can render anything, the queue needs a home, a lifecycle, and an API contract.

Scope decision (user-approved): build the **BFF first**, defer the React frontend to the next slice. The BFF is the contract-defining, Python-native, locally-verifiable piece — it stays in the repo's proven FastAPI+pytest pattern and de-risks the Node-toolchain pivot. Its emitted OpenAPI becomes the contract the React slice consumes.

## Decision

Build the BFF as `services/agent-spine/src/trax_io_spine/bff/` (behind a `[bff]` extra), reusing the existing pipeline rather than reimplementing it.

- **`PlannerStore`** is an in-memory, per-tenant store. `from_extract` runs the real `build_stores_from_extract` → `RecommendationService` → `GuardrailEnforcer`, **keeping the `(Recommendation, GuardrailOutcome)` pairs the Supervisor discards** — so queue rows carry full recommendation context and the detail view carries real provenance. A lifecycle state machine (`PENDING / APPROVED / REJECTED / DEFERRED`) sits over the entries; approvals flow through `InMemoryWritebackTarget` (the #6 hardened seam — history + rollback).
- **`create_planner_app`** wraps the store in FastAPI: priority-sorted queue, provenance detail, approve / reject (categorical reason) / defer, bulk-approve by filter, writeback history, rollback, and a per-tenant kill switch. Store exceptions map to HTTP status: unknown tenant/rec → `404`, approve-no-policy → `409`, bad body → `422`, action-while-kill-switch-engaged → `423`.
- **Real provenance, not fabricated.** Grounding initially over-claimed a nested `DemandProjection` on the recommendation; the contract actually exposes `projected_demand` (scalar) + `policy`/`current_policy`/`supporting_evidence`. The `RecommendationDetail` uses the real fields.
- **Tenant isolation** is structural: one `PlannerStore` per tenant in the app's `stores` dict, each with its own writeback target; a foreign `recommendation_id` is simply unknown → `404`. A two-tenant test pins it (CLAUDE.md's 4-layer isolation rule).

## Consequences

**Positive**
- The approval queue finally has a home and a lifecycle; the full loop is locally verifiable (queue → provenance → approve → writeback + history → queue shrinks), no AWS/eMRO/auth. 24 BFF tests; 112 agent-spine tests green; live-verified.
- The BFF reuses the engine/guardrail/supervisor/writeback unchanged — zero duplication of decision logic.
- The emitted OpenAPI is the contract the React frontend slice builds against, so the toolchain pivot is de-risked.

**Negative / deferred**
- **The React frontend is the next slice** (greenfield React 18 + TS + Vite).
- In-memory store (no DynamoDB persistence); `tenant_id` is a trusted path param (JWT + Cedar auth stubbed); no SSE real-time updates.
- Deferred UI surfaces: the weekly Tier-C digest, autonomy-band / service-level settings, bulk-rollback + confirmation token, the NL-explanation agent, the monthly BVR PDF, the federated override-feedback loop.
- Kill switch is v1-simple (engaged ⇒ approve/bulk-approve `423`); the "revert to shadow within 60s" runtime propagation is a real-deployment concern, deferred.

## Alternatives considered

1. **Extend the read-only reco-API.** Rejected: the reco-API is a stateless recommendation browser; the approval queue is a stateful workflow above the Supervisor, with writeback side effects. Different responsibility.
2. **A new standalone `services/planner-api` package.** Reasonable, but the BFF needs the Supervisor, the contracts, the guardrail, and `InMemoryWritebackTarget` — all in agent-spine. A `bff/` module behind a `[bff]` extra reuses them with zero new package wiring.
3. **Build the React frontend first (mockup) or together.** Rejected (user decision): BFF-first defines the contract and keeps the slice in the proven Python pattern before the Node-toolchain pivot.
