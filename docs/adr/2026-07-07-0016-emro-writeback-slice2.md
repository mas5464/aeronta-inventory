# ADR-0016: Slice 2: three domains, one ledger; contract-complete rollback

**Date:** 2026-07-07
**Status:** Accepted
**Context project:** #6 eMRO Writeback REST API (real-eMRO Java track, slice 2)

## Context

[ADR-0015](2026-07-07-0015-emro-writeback-java-service.md) shipped slice 1's `StockLevelWriter` core, both facades, and Kafka — but deferred rollback, the audit-supplement history endpoint, requisitions, transfers, replay tooling, an exception taxonomy for the unreachable Kafka infra-retry path, and the real-Oracle audit-PK same-second collision risk. The user's scope decision for slice 2 was explicit: *everything remaining* — the full PRD completion plus the Trax IO #6 seam gaps — landed as one slice, one stacked branch (`claude/emro-writeback-slice-2` on slice 1's `ab98590`), to keep PR #4 clean (D9).

The [slice-2 spec](../superpowers/specs/2026-07-07-emro-writeback-java-slice2-design.md) records nine new decisions, D9–D17. This ADR supplements ADR-0015; it does not supersede it — slice 1's core architecture (one domain core, thin facades, canonical commands, trust-caller-record-provenance) stands unchanged.

## Decision

Extend the slice-1 architecture with two new domains sharing the existing ledger, and close every documented slice-1 carry-forward.

- **D10 — Ledger extension.** `WRITEBACK_LEDGER`'s Flyway `V1` amended in place (still pre-deployment, same amend-not-version-bump judgment call ADR-0015 already made twice): a `DOMAIN` column (`STOCK_LEVEL`/`REQUISITION`/`TRANSFER`, `NOT NULL`) and a `CREATED_REF` column (the requisition/order number, for replay + duplicate-replay responses) were added, and `MESSAGE` — dead since slice 1 — is now populated with the per-row outcome message via a shared `messageFor` helper, so `ItemResult` and the ledger row agree by construction.
- **D11 — eMRO number sources behind a seam.** `RequisitionNumberSource`/`OrderNumberSource` abstract the real eMRO sequence calls (`PKG_APPLICATION_FUNCTION.config_number('REQSEQ'|'POSEQ')`); test implementations use plain DB sequences, since the real packages don't exist in Dev Services. Same trick as `fake_emro` in the Python seam: contract-tested logic, real dependency isolated.
- **D12 — Rollback, contract-complete.** Extracted from the Python contract test-for-test: revert the latest `WRITTEN` entry with non-null `old_values` by applying it as a **new write** (new version; `parent_version` → the reverted version; provenance `rollback:{provenance_id}`; principal from the request, default `planner`). `NOTHING_TO_REVERT` when there are no writes or only a first write; `OUTSIDE_WINDOW` beyond a configurable, never-zero window (default 90 days).
- **D13 — Out-of-band history as a separate endpoint.** `GET /traxio/v1/history/out-of-band` lists `PN_INVENTORY_LEVEL_AUDIT` rows whose `MODIFIED_BY` isn't one of this service's own principals, in its own DTO (values, timestamps, `modified_by`, deliberately no fabricated `version`). The contract `/history` endpoint stays byte-compatible with `HistoryEntry` — fabricating a monotonic version for an audit-only row that never went through the ledger would corrupt the contract.
- **D14 — Kafka domain discriminator.** One topic, one consumer; the batch message gains an optional `domain` field (`stock_level` default | `requisition` | `transfer`) that routes to the matching processor via a generic route/`DomainProcessor` dispatch. Missing `domain` = slice-1 behavior, so this is backward compatible. REST facades stay separate per domain, unchanged.
- **D15 — Exception taxonomy.** A new unchecked `InfrastructureException`, thrown by the writer/creators only for connection-class failures (`SQLTransientException`, `SQLNonTransientConnectionException`, connection-acquisition failures — never constraint violations or validation), makes the Kafka path's 3-attempt-retry-then-DLQ genuinely reachable for the first time (closing ADR-0015's "infra-retry unreachable" carry-forward) without touching the REST path's always-200, per-row-`ERROR` contract, which stays exactly as slice 1 shipped it.
- **D16 — Thin replay.** `GET /api/v1/runs/{runId}/results` re-emits recorded per-row results from the ledger (`writeback:read`), tenant-scoped, ordered oldest-first by `createdAt` then `rowId`. Full payload re-drive for a run is a Kafka-retention/consumer-offset-reset operation, documented in the README, not a service responsibility — rejected rows are deliberately never ledgered, so there is no archive to replay them from.
- **D17 — Audit-PK collision mitigation.** eMRO's audit-table primary key (including a second-precision `CREATED_DATE`) can't be altered — it's their schema, not ours. A real Oracle `ORA-00001` whose message text matches `PN_INVENTORY_LEVEL_AUDIT` is now classified and given a bounded 2-attempt retry with a ≥1.1-second backoff (long enough for `CREATED_DATE`'s second-precision to advance), converting a same-second same-key collision from an immediate `500` into a self-healing retry. Applies to the stock-level writer only.
- **Requisitions and transfers** each got their own creator (`RequisitionCreator`, `TransferCreator`) following slice 1's validated/ledgered/effectively-once shape, entities lifted byte-for-byte from ARMAC, and batch + Trax IO facades sharing a single extracted `WireSanitizer` helper (closing a duplication risk the slice-1 facades had each solved separately).

## Deviations & discoveries

1. **`parent_version` chaining diverges from `fake_emro` when a shadow write intervenes.** The Java writer chains `parent_version` to the max version seen (including shadow writes); the Python `fake_emro` chains to the last *written* (non-shadow) version. This is pre-existing slice-1 writer behavior, not part of the rollback contract, and unpinned by any Python history test — documented as a deviation rather than changed, since the chain-integrity tests written against it are version-agnostic and both behaviors are internally consistent.
2. **The run-results envelope is a bare JSON array, not `{runId, results}`.** The slice-2 plan's brief text assumed an enveloped shape; the implementation and the controller's own re-derivation from the PRD batch surface's conventions agree the top-level array is correct (matching `BatchResource`'s own camelCase convention) — the brief text drifted, not the code.
3. **Currency is deliberately `null` on transfer orders.** ARMAC hardcodes a `QAR` currency constant on the legacy `OrderHeader`; this service's `TransferCreator` does not port that hardcode, since Trax IO has no currency input for a stock transfer and inventing one would be a fabrication, not a lift.
4. **`orderOption1..10` and `shippedFromLocation` audit-row omissions.** ARMAC's `OrderDetailAudit`/`OrderHeaderAudit` track ten free-text option slots the legacy UI used for operator remarks; this creator writes none of them (Trax IO has no equivalent input). `shippedFromLocation` is set on `OrderHeader` but not mirrored onto its audit row, matching `RequisitionCreator`'s existing precedent of auditing only the fields the creator itself derives.
5. **`needBy` divergence.** `RequisitionCommand.needBy()` maps to `RequisitionDetail.requireDate` at start-of-day UTC; ARMAC's original also derives `requireHour`/`requireMinute`, which this creator leaves unset (Trax IO's `needBy` is date-only, not a timestamp — inventing hour/minute precision would be a fabrication).
6. **The `ORA-00001` message-text assumption (D17) is unverified against real Oracle.** D17's classification, and the pre-existing LEVEL_ROW_RACE retry it extends, both assume Oracle's `ORA-00001` error text reliably contains the colliding table's name in this eMRO instance's NLS/error-format configuration. That can only be confirmed from a real production error-log sample, not a read-only smoke probe (see `EmroSchemaSmokeTest`'s class-level Javadoc, added by this task's smoke extension) — tracked as a carry-forward, not treated as verified.
7. **Entity-type fidelity rule reaffirmed.** T7 (transfers) initially drifted from ARMAC's native `long`/`BigDecimal` column types on `OrderHeaderPK`/`OrderDetailPK`/`OrderDetail.batch` during first-pass implementation; adversarial review caught it and the fix (commit `1f77857`) restored the primitive types across all four order PKs plus a numeric `TestOrderNumberSource`, explicitly matching the precedent requisitions' own `RequisitionHeader.requisition`/`RequisitionDetailPK` had already set by staying native `long` since their entity lift (T4/T5). Reaffirms the slice-1 rule that lifted entities must match the ARMAC reference field-for-field, including primitive type, not just column name.

## Consequences

**Positive**
- One ledger now records all three domains (`DOMAIN` column) with a genuinely populated `MESSAGE`, closing slice 1's dead-column carry-forward and giving replay (D16) real per-row detail to re-emit.
- The Kafka infra-retry path is reachable for the first time since slice 1 shipped — connection-class failures now genuinely retry-then-DLQ instead of silently degrading to per-row `ERROR`.
- Rollback, requisitions, and transfers all follow the same validated/ledgered/effectively-once shape slice 1 established, and requisitions/transfers share one `WireSanitizer` instead of two independently-maintained copies.
- **143 tests green** (144 after this bookkeeping task's own ordering-pin addition), subagent-driven TDD + per-task adversarial review, three times with a Needs-fixes → fix → re-review round (T5's real-schema fields, T6's shared sanitizer, T7's type fidelity) that caught real defects before they reached main.

**Negative / carried forward (tracked in ROADMAP #6)**
- **D17's `ORA-00001` message-text assumption is unverified against real Oracle** (deviation 6 above) — needs a production log sample before the audit-PK retry can be trusted at face value on a live instance.
- **`RollbackServiceTest` has a pre-existing concurrency-timing flake** that self-resolves on rerun — not chased down in slice 2, triaged as acceptable at the final review.
- **Physical stock-move side effects remain out of scope.** `TransferCreator` creates the `ORDER_HEADER`/`ORDER_DETAIL` rows a transfer needs but does not move physical inventory records (`PnInventoryDetail`/`PnInventoryHistory` writes ARMAC's original performs) — documented, matching `RequisitionCreator`'s existing trim discipline.
- Production IdP, broker, and deployment; a live smoke-test run against `oracle19c` (now also covering the requisition/order table and `PKG_APPLICATION_FUNCTION` existence checks this task added); `NotePad`/remarks fields; and a PRD Phase-4 load test against NFR numbers all remain deferred to a future slice.

## Alternatives considered

1. **Split slice 2 into per-domain sub-slices (rollback, then requisitions, then transfers, ...).** Rejected per the user's explicit "everything remaining, one slice" scope decision (D9) — the goal was a single stacked branch keeping PR #4 clean, not incremental review checkpoints.
2. **Give requisitions and transfers their own idempotency ledgers.** Rejected: it would reintroduce exactly the drift risk ADR-0015 designed against for stock-level vs. batch facades — one ledger, one idempotency rule, now for all three domains via the `DOMAIN` column (D10).
3. **Skip the exception taxonomy (D15) and leave the Kafka infra-retry path unreachable.** Rejected: it was an explicitly tracked carry-forward from ADR-0015's own "Negative" section, and the fix (a narrowly-scoped new exception type, not a rework of the reviewed core) was judged low-risk enough to include in this slice rather than defer again.
