# Sub-plan #7 — Planner UI "Trax IO Review" Implementation Plan

**Goal:** Ship the planner-facing UI surface embedded inside eMRO that lets the customer's planning lead review, approve, reject, defer, and bulk-action Trax IO recommendations. This is the only new UI surface the customer sees; its usability determines planner trust, which determines the product's survival at renewal time.

**Owner:** eMRO product team (frontend) + Trax IO platform (backend-for-frontend + approval-queue API).

**Format:** Integration-plan format (like #3 and #6). Frontend follows eMRO's existing web conventions; backend is Trax-hosted.

**Tech Stack:** eMRO's established frontend stack (React if current eMRO is React-based; server-rendered templates otherwise — the eMRO team calls this). Trax-side backend-for-frontend is Python FastAPI on AgentCore Runtime alongside the Supervisor. PDF rendering handled by sub-plan #8 (BVR).

---

## What the planner actually needs to do

Based on my 25 years of planner interactions and design §6.3, the UI must support the following core workflows without friction:

1. **Morning review.** Planner opens UI, sees their queue sorted by `priority_score = criticality × cost × |delta|`, scans the top ~20 recommendations, bulk-approves the obvious ones, opens the non-obvious ones for provenance review.
2. **Provenance drill-down.** Click any recommendation → see the regime classification, the forecast distribution (mean + tails, with peer-part comparisons for ultra-rare), the lead-time distribution, the current vs. proposed values, the hard-guardrail status, and a natural-language explanation generated by the Supervisor agent.
3. **Bulk approve by filter.** "Approve all tier-4 expendables with |delta| < 10% and essentiality >= 4" — one click, 200 recommendations gone.
4. **Reject with reason.** Reject a recommendation with a categorical reason (wrong-for-fleet / wrong-essentiality / bad-lead-time / planner-override-current-value / other+free-text). Reasons feed back into the model evaluation pipeline as training signal (override rate).
5. **Defer.** "Not now, check again next week" — pushes the recommendation to a 14-day future queue.
6. **Rollback a Tier B/C write.** One-click rollback of a recommendation that was auto-applied but is now wrong.
7. **Bulk rollback (the emergency button).** "Revert all agent writes from yesterday." Requires two-step confirmation, logs loudly.
8. **Kill switch.** "Pause the agent for my tenant." One toggle, propagates within 60 seconds.
9. **Weekly digest.** Planner sees the past week's Tier C auto-applied writes as a digest with ability to retroactively flag any of them as wrong.
10. **Configure service-level targets + autonomy bands.** Planner can tighten/loosen the defaults per criticality tier.
11. **Review the monthly Business Value Report.** PDF posted to the UI; planner can forward to their CFO.

## Phases

### Phase 0: UX design + workflow validation (3 weeks)

- Design sessions with lighthouse customer's planning lead. Iterate on wireframes for the morning-review workflow above.
- Usability test with 2 other candidate customer planners.
- Lock information architecture: tabs = `Queue | History | Bulk Actions | Digest | Reports | Settings | Kill Switch`.
- Design spec handed to frontend engineers.

### Phase 1: Backend-for-frontend (5 weeks)

**Files:** Trax IO platform ships a new FastAPI app `trax-io-planner-bff`. Lives in the Agent Spine repo under `src/trax_io/bff/`.

Key endpoints (all mTLS + JWT from eMRO's embedded iframe/widget host):

- `GET /v1/tenants/{tenant_id}/recommendations?status=pending&sort=priority&limit=50` — paginated queue.
- `GET /v1/tenants/{tenant_id}/recommendations/{id}` — full detail with provenance.
- `POST /v1/tenants/{tenant_id}/recommendations/{id}/approve` — calls Writeback Agent to write.
- `POST /v1/tenants/{tenant_id}/recommendations/{id}/reject` — records rejection with reason.
- `POST /v1/tenants/{tenant_id}/recommendations/{id}/defer` — pushes to future queue.
- `POST /v1/tenants/{tenant_id}/recommendations/bulk-approve` — body = filter.
- `GET /v1/tenants/{tenant_id}/digest/weekly` — week's Tier-C writes.
- `POST /v1/tenants/{tenant_id}/killswitch` — body = `{engaged: bool}`.
- `GET /v1/tenants/{tenant_id}/reports/monthly/{YYYY-MM}` — streams PDF from sub-plan #8.
- `GET|PUT /v1/tenants/{tenant_id}/settings/service-levels` — per-criticality fill rate targets.
- `GET|PUT /v1/tenants/{tenant_id}/settings/autonomy-bands` — per-tier delta caps, cost thresholds.

Each endpoint enforces tenant + planner principal matching. Every mutating call is audit-logged.

### Phase 2: Natural-language explanation agent (2 weeks)

Supervisor exposes a new tool `explain_recommendation(id)` that produces a 2–4 sentence plain-English explanation of a recommendation. Uses Claude Sonnet with a constrained prompt: "Given this provenance record and this forecast distribution, explain to a maintenance planner what changed and why."

Cached per recommendation; 24h TTL.

### Phase 3: Frontend — queue + detail views (6 weeks)

- Queue view: sortable table, row colors by tier (A=yellow, B=blue, C=green), priority-score column, "approve" button per row, bulk-select checkbox.
- Detail view: 2-column layout. Left = current vs proposed values with diff callouts; right = provenance card with forecast-distribution chart, lead-time chart, peer-part comparison for ultra-rare, natural-language explanation.
- Inline buttons: Approve / Reject (with reason dropdown) / Defer / Rollback (if already applied).

### Phase 4: Frontend — bulk actions + digest + reports (4 weeks)

- Bulk actions page with filter builder UI.
- Weekly digest table with "flag as wrong" per row.
- Reports tab with monthly BVR PDF viewer + download.

### Phase 5: Frontend — settings + kill switch (2 weeks)

- Settings forms for service-level targets and autonomy bands.
- Kill-switch toggle with confirmation modal; status indicator visible on every page when engaged.

### Phase 6: Contract tests + accessibility (2 weeks)

- Playwright end-to-end tests covering all 11 workflows.
- Accessibility audit (WCAG 2.1 AA): keyboard navigation through queue, screen-reader friendly recommendation detail view, high-contrast mode, focus management.

### Phase 7: Staged rollout (4 weeks)

- Deploy to lighthouse customer with kill switch initially ENGAGED (read-only UI).
- Planner reviews 30 days of shadow-mode recommendations retrospectively to build trust.
- Kill switch disengaged; Tier-C writes begin; planner sees them appear in the Digest tab.
- Tier B and A autonomy enabled incrementally per sub-plan #10's onboarding.

### Phase 8: Ship in eMRO release

Cut with sub-plan #6 Writeback REST into the same eMRO release where possible.

## Cross-cutting concerns

- **Real-time updates.** New recommendations appear in the queue without a page reload. Server-sent events from the BFF; frontend reconnects automatically.
- **Latency.** Queue load < 500ms for 1000 pending items. Detail view < 800ms including forecast-chart render.
- **Localization.** English + French + Spanish + Portuguese in v1 (common MRO-operator languages); German + Japanese in v1.1.
- **Audit.** Every UI action logged with planner principal, tenant, timestamp, action, target recommendation.
- **Security.** Iframe sandboxing in eMRO host; CSP strictly configured; no cross-tenant data leakage possible through the frontend.

---

## Deliverables

From eMRO team: frontend module integrated into eMRO, Playwright test suite, accessibility audit report, localization files for launch languages.

From Trax IO platform: BFF service (`trax-io-planner-bff`), OpenAPI spec, explanation-agent prompt + evaluation harness, integration tests against the Agent Spine.

---

## Risks

- **Planner adoption.** The #1 product risk. Mitigation: weekly office hours with the lighthouse planner during Phases 3–7. Iterate on the queue view based on observed behavior.
- **Information overload.** 1000+ pending recommendations is demoralizing. Mitigation: smart defaults in bulk-approve, priority-score sorting, regime-based grouping.
- **Explanation quality.** Bad explanations erode trust faster than no explanations. Mitigation: Phase 2 includes an explanation-quality eval harness with known-good examples; planner team signs off on samples before launch.

- Phase 6: 2 weeks.
- Phase 7: 4 weeks.
- Total: ~21 weeks elapsed with 2 frontend engineers + 1 platform engineer + 0.5 designer.
